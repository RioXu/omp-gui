新增默认回归覆盖发现缓存（同项目连续 11 次发现只启动一次假 OMP）、跨项目隔离、历史投影共享及外部日志删除通知、合并路径和 POSIX 反斜线、二进制类型化枚举／完整 Session 请求、Unicode／数值边界、畸形归档／长度／容器及超大响应错误后通道存活。

显式 Linux 进程集成测试 binary_management_watch_and_supervised_release 使用真实 OMP 和全新临时 profile／项目，验证管理握手、原始附件字节上传、会话索引、二进制文件通知、竞争 owner 被拒、桥断开后重附着、状态查询、空闲释放及原生锁可用。仅配置虚拟模型身份供 OMP 启动，不发模型请求。此测试直接启动 helper 进程，覆盖 stdio／Unix socket／原生 OMP 协议边界，不能代替真实跨主机 SSH 应用协议回归；源码上传和远端构建本身通过已有 SSH 主机完成。

### rkyv 合成基准

Linux x86_64 release，对同一数据分别执行编码与完整解码，单次样本；包括归档验证，不包括 SSH、OMP 启动、磁盘及 GUI 渲染。直接通过 Serde 适配平坦 rkyv 归档，不包装 JSON 文本，不构造中间 JSON Value 树。

| 数据 | 次数 | JSON 字节／次 | rkyv 字节／次（含帧头） | JSON 总耗时 | rkyv 总耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 小事件 | 20000 | 72 | 123 | 14.41 ms | 24.50 ms |
| 合成历史，2000 条消息 | 20 | 4280904 | 4344043 | 180.00 ms | 95.81 ms |

该大历史样本编解码耗时约下降 47%；小事件增加约 0.5 微秒／次，体积也更大，不能宣称 rkyv 对所有消息都更快。旧管理大响应还需 Base64 分片，此表用裸 JSON 作保守对照；不据此推断端到端收益。普通附件上传不再承担 Base64 体积增量。其他五项优化目前有行为与进程次数证据，尚无 CPU／RSS 或真实大项目 P95 的量化对照。

复现命令：

~~~sh
RUST_MIN_STACK=8388608 cargo test -p omp-core -p omp-gui-remote -- --test-threads=1
OMP_GUI_TEST_OMP=/absolute/path/to/omp cargo test -p omp-gui-remote --test transport -- --ignored --nocapture
RUST_MIN_STACK=8388608 cargo test --release -p omp-core transport_roundtrip_benchmark -- --ignored --nocapture
~~~

### 流式 JSON 帧解析比较

测试实现位于 `crates/omp-core/src/infrastructure/omp/stream_json_bench.rs`，simd-json 已接入生产接收路径。复现桌面程序实际启用的 serde_json 特性：

```powershell
cargo test --locked -p omp-core --release --features serde_json/preserve_order,serde_json/raw_value stream_json_performance -- --ignored --nocapture
```

2026-11-02，Windows x64、i7-11800H、Rust 1.97.1；serde_json 1.0.154、sonic-rs 0.5.10、simd-json 0.19.0，默认分配器和通用编译目标。构建完成后单独运行，不与编译并行；每种负载各测 9 轮，每轮各实现累计至少 80 ms，轮换测试次序，表中为每帧平均耗时的中位数（µs，越低越好）。

| 合成 OMP 帧 | 平均字节数 | serde_json | sonic-rs | simd-json 复制输入 | simd-json 可变输入 | simd-json 可变输入＋复用 Buffers |
|---|---:|---:|---:|---:|---:|---:|
| 短文本增量 | 234 | 4.126 | 4.124 | 4.373 | 4.277 | 3.525 |
| 累积增长的消息快照 | 38,340 | 84.130 | 61.904 | 67.276 | 63.999 | 59.211 |
| 含嵌套任务的工具事件 | 6,031 | 78.925 | 76.178 | 72.366 | 72.259 | 70.323 |
| 512 KiB base64 传输分片 | 524,382 | 220.683 | 190.895 | 1004.143 | 685.489 | 292.736 |

所有实现均生成当前应用使用的 `serde_json::Value`，包含解析、输出分配和释放，不包含网络、文件读取、消息合并和界面渲染。模拟接收所需的初始输入缓冲分配对所有实现统一排除；“复制输入”额外计入适配原先 `Decoder::decode(&[u8])` 的复制成本。“可变输入”直接消费接收线程已有的 Vec；复用 Buffers 另保留解析器内部暂存区。正确性测试逐帧比较三库的输出。上表为接入前的对比记录，默认 simd-json 特性；最新生产复测额外启用 big-int-as-float 兼容旧解析行为。

普通流式事件中，复用 Buffers 的 simd-json 相比原先 serde_json 解析耗时降低约 11%–30%，相比 sonic-rs 降低约 4%–15%；大分片仍是 sonic-rs 更快。生产路径据此采用小于 256 KiB 的帧走 simd-json 并复用 Buffers，较大帧及重组正文走 sonic-rs，接收 Vec 也跨帧复用。基准新增 Production 实现，直接调用生产 JSON 分流函数，包含大帧嵌套深度预检查；仍不包含完整分片组装或界面处理。保存路径继续使用 sonic-rs。

接入后的独立复测（同一机器、命令和 9 轮中位数，simd-json 已启用 big-int-as-float，单位 µs／帧）：

| 合成 OMP 帧 | 同轮 serde_json 基线 | 生产分流函数 | 解析耗时降低 |
|---|---:|---:|---:|
| 短文本增量 | 4.117 | 3.655 | 11% |
| 累积增长的消息快照 | 86.879 | 58.617 | 33% |
| 含嵌套任务的工具事件 | 81.117 | 71.282 | 12% |
| 512 KiB base64 传输分片 | 218.407 | 207.242 | 5% |

大帧的生产结果包含嵌套预检查，因而略慢于直接调用 sonic-rs，仍优于原解析路径。流式解析阶段当时通过格式检查、全 workspace Clippy、117 项默认测试及本地构建，另有 20 项显式测试保持忽略；这些计数仅对应当时的代码阶段。此处单独运行了上述发布模式基准。

协议回归测试覆盖两条路径在 256 KiB 阈值附近切换、复用输入后旧事件仍然有效、中文与代理对及转义、64 位边界和超大整数浮点退化、非法 UTF-8／JSON／尾随数据、与旧解析器一致的容器嵌套上限、字符串中括号不计入嵌套，以及分片乱序、重组正文校验和大小限制。

## GPUI Fast 后端对比

2026-11-03，Windows x86_64，i7-11800H／RTX 3060 Laptop，使用当时 v0.8.4 代码比较 `gpui-pre 0.3.10` 与 `gpui-fast 0.1.12`。两组采用相同优化开发配置（应用 opt-level=1、依赖 opt-level=2）、相同锁文件、1240×850 窗口、曜石橙皮肤及 60Hz 显示器；报告中的 refresh_ms 均为 16.666667。共同的合成会话含 32 段中文／英文、公式与 Rust 代码，助手正文 6487 字符；使用隔离项目，不连接原生会话、不发模型请求。

构建全部结束后再采样，后端交替运行。每个后端／场景重复 3 次，每次预热 3 秒、执行 48 次动作；12 组 active_switches 均为 48。表中绘制耗时为“每轮平均值”的中位数，P95 为“每轮提交间隔 P95”的中位数，不混同于一次合并分布的 P95。

| 场景 | pre 平均绘制 | Fast 平均绘制 | 绘制耗时变化 | pre P95 提交间隔 | Fast P95 提交间隔 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 工作面板页签切换 | 11.83ms | 9.58ms | −19.0% | 18.32ms | 19.21ms |
| 弹窗打开／关闭 | 12.64ms | 10.41ms | −17.7% | 18.66ms | 19.37ms |

页签单轮平均绘制范围：pre 11.79–11.89ms、Fast 9.56–10.06ms；弹窗：pre 12.63–12.77ms、Fast 10.15–10.51ms。主要收益来自预绘制（页签 7.59→5.87ms，弹窗 8.05→6.26ms），布局阶段没有改善。两组共记录 7290 个 Draw 样本；Fast 实际提交／绘制次数也略多，不能把每帧降幅直接解释为进程总 CPU 占用降幅。

结论：Fast 能稳定减少这两个场景的每帧绘制开销，但 P95 提交间隔略差，两组均超过 60FPS 的 16.67ms 预算。当前保留 pre 为默认，Fast 作为显式可选实验后端；没有宣称解决长帧，也没有将上游 Linux 基准当作本应用收益。未测 release 配置、真实模型流式输出和大型工程滚动，不外推这些场景。

复现时先准备同一份隔离演示数据，再分别构建并保存程序；保持两组数据副本初始内容一致，采样期间关闭编译等额外负载：

```powershell
cargo build --locked --features frame-profile
Copy-Item target/debug/omp-gui.exe artifacts/gpui-pre-ab.exe
cargo build --locked --features frame-profile,gpui-fast
Copy-Item target/debug/omp-gui.exe artifacts/gpui-fast-ab.exe

artifacts/gpui-pre-ab.exe --demo --data-dir artifacts/gpui-ab/pre-tabs-1 --frame-profile-hz 60 --frame-profile-output artifacts/gpui-ab/pre-tabs-1/report.json --frame-profile-exit
artifacts/gpui-fast-ab.exe --demo --data-dir artifacts/gpui-ab/fast-tabs-1 --frame-profile-hz 60 --frame-profile-output artifacts/gpui-ab/fast-tabs-1/report.json --frame-profile-exit
```

弹窗组追加 `--frame-profile-dialogs`；每轮使用新的相同数据副本并指定独立报告路径。`--frame-profile-exit` 在报告写完后关闭本次演示程序；分析器会先等待窗口激活，再开始预热。普通试用可执行 `cargo run --locked --features gpui-fast -- --demo --data-dir artifacts/fast-demo`，省略分析参数即可正常交互。

本地原始数据位于 `artifacts/gpui-ab/{pre,fast}-{tabs,dialogs}-{1,2,3}/report.json`，合成初始数据为 `seed.json`，汇总为 `summary.json`（均不提交）。两个后端共用 gpui-kit 的分析／测试接口；Windows CI 分别运行默认测试与 Fast 桌面测试。

## 原生动画帧率基准（v0.8.2 历史）

2026-11-02，相同公式长回复隔离副本、前台窗口、每组 48 次动作，原生 Draw／Present 实测如下。全部组的 `active_switches` 均为 48；高刷组屏幕刷新率为 165Hz。表中 FPS 指连续动画帧的提交频率，60Hz 显示器的物理显示仍最多为 60 FPS。

| 场景 | 平均绘制 | 平均动画提交频率 | P95 提交间隔 |
| --- | --- | --- | --- |
| 未优化开发构建，165Hz 标签 | 42.30ms | 22.6 FPS | 48.45ms |
| 优化开发构建，165Hz 标签 | 7.50ms | 91.3 FPS | 19.18ms |
| 优化开发构建，165Hz 弹窗 | 6.99ms | 73.8 FPS | 25.30ms |
| 优化开发构建，60Hz 标签 | 6.11ms | 113.6 次／秒 | 15.06ms |
| 优化开发构建，60Hz 弹窗 | 6.48ms | 113.7 次／秒 | 14.63ms |

60Hz 两组分别包含 658／1000 个连续动画提交间隔；P95 均低于 16.67ms。仍存在少量约 19ms 的长帧，不承诺系统任意负载下零掉帧。原始本地报告为 `artifacts/native-frame-baseline.json`、`native-frame-optimized-{tabs,dialogs}.json`、`native-frame-60-{tabs,dialogs}.json`（均不提交）。

使用含长回复与公式的隔离演示数据，保持窗口处于前台、关闭其他测试负载。以下命令只在 `--demo` 和显式 `--data-dir` 同时存在时启用自动切页，不发送模型请求；普通构建不包含分析器。

```powershell
cargo build --locked --features frame-profile
target/debug/omp-gui.exe --demo --data-dir artifacts/math-qa/data --frame-profile-output artifacts/native-frame-tabs.json
```

预热 3 秒后，每 220ms 切换一次原生页签，共 48 次；约 14 秒生成 JSON。关闭该隔离窗口后，可在同一命令追加 `--frame-profile-dialogs`，另指定输出文件，验证 24 次弹窗打开／关闭。原始样本包含 GPUI 的布局、预绘制、绘制和平台提交时间，以及连续动画帧的实际提交间隔。`active_switches` 必须为 48，否则前台采样无效；空闲不绘制的间隔不计入 FPS。`summary` 汇总平均 FPS 与 P95 帧间隔。提交间隔是原生运行时指标，不等同于显示器物理扫描输出。

多显示器验证可追加 `--frame-profile-hz 60`，由 GPUI 选择刷新率匹配的显示器；必须再检查报告内的 `refresh_ms`，匹配失败会使用默认屏幕。该参数仅在启用分析功能的演示构建中生效，不修改系统显示设置。
